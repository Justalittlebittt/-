## 1. 产品目标与硬约束

原创动物园主题的二维多格动物拼图：选择动物、拖拽、90°旋转、放置、完成棋盘、进入下一关。首版仅“运输与入园安置”章节，必须包含清晰的开始、教学、可玩关卡、完成反馈和章节结束。Steam 是目标发行方向，商店流程与制作工期分开计算。

目标是尽快完成可发布游戏、获得真实玩家反馈；利润不是首要指标。首版完整可发布构建的开发周期暂定最多 7 天，只能经 HUMAN 同意调整；不能以原型、管线通过或静态展示图代替完整交付。正式进入制作前记录开发计时起点、结束条件、内容上限和返工预算；前期探索另行记账、限制投入，不允许无限前期准备规避上限。超预算优先缩范围、停止或重新提案，不默认延期。

首版不默认加入经营经济、养成、多章节、复杂叙事、骨骼动画或实时 3D 动物。物种、姿态、关卡、拼块形状的数量由实际最低完整体验及 7 天预算确定，不照搬历史数量提议。优先使用免费可获得且权利清晰的工具/资源；不得复制其他游戏关卡、素材或影视角色的具体设计。

## 3. 核心玩法、关卡与体验

- occupied_cells 唯一决定棋盘二维放置和碰撞，不是动物脚掌、地面投影或三维体积；由非空、无重复、四邻接连通整数格组成。逻辑格与绘制图像通过同一锚点执行 90°旋转和定位；镜像不当作旋转。
- DESIGN 提出有限形状候选 → ART 反向匹配物种与姿态并评估可爱度/识别度 → DEV 核验数据和实现 → DESIGN 在可行集合中冻结关卡所需组合。不得为了难画的物种无上限增加形状和素材。
- 关卡入库至少证明初始状态有一条合法解、完成判定正确、教程可理解、难度安排有说明，并检查近似重复关卡。**不要求唯一解，也不要求玩家任意错误操作后仍然必有解**；游戏必须提供足以从死局恢复的撤销或重试方案，由 DESIGN 在首版范围中冻结。
- 真实交互验收关注选择、拖放、旋转、合法/非法提示、格子对齐、完成反馈、下一关和章节结束；实际试玩和玩家反馈不可由“解算器通过”或 AI 自评好玩代替。
- 网格高亮、拖拽投影、合法位置预览可以帮助读格，但不得掩饰大片隐形占格、主体轮廓不匹配或明显侵入邻格。占格、像素轮廓和点击命中区域分离。
- 允许动物整图旋转后呈现非真实重力姿态，但须在真实棋盘检验四方向的识别、遮挡和违和；影响体验时由 DESIGN 与 ART 改姿态/提示或调整形状需求，DEV 不得私改逻辑规则。

### 3.1 首章范围、UI 与场景生产规则（V1.4 新增）

1. **先定功能与内容边界，再做正式视觉**：DESIGN 在 G0 汇总首章最小可发布的关卡、形状、动物素材预算及返工上限，同时明确实际棋盘宽高范围、最大同时可见拼块数、屏幕/输入设备目标和必要界面状态。先用占位图验证布局；参数未由 HUMAN 批准前不写死固定关卡数、尺寸或资产配额。允许 DESIGN/ART 提前探索单张布局概念，不等于冻结正式界面。
2. **动态布局而非固定坐标拼贴**：棋盘、动物待放置区、标题/关卡进度与操作区按真实棋盘尺寸、拼块旋转包围盒及可用视口安排；必须互不遮挡、拼块可完整抓取、拖放/旋转/预览与缩放坐标一致。不能依赖只在示例三关成立的固定托盘 Y、固定棋盘行数或固定画布尺寸；无需为假设的全平台开发通用布局框架。DEV 对首发最小/最大棋盘、最多拼块及目标缩放进行可复现浏览器验证。
3. **视觉审查图不等于游戏资源**：ART 可提交一张完整游戏画面用于 HUMAN 判断风格和布局，但正式交付应拆分必要的独立背景/装饰/视觉规范与可复用界面组件；棋盘格、按钮、进度、合法性预览优先由 DEV 复用现有 HTML/Canvas 实现。禁止把静态整页图当作可交互 UI，或为换皮重写拼图核心。首章优先一套静态背景；折叠面板/装饰动画仅在具体功能需要且预算允许时加入，此限制**不涉及动物可自由折叠、卷曲的造型**。
4. **按关卡需要增产动物**：DESIGN 先验证每个新形状确有解谜作用和至少一个可用关卡，再向 ART 请求对应的有限动物素材；同一动物/同一姿态/同一占格允许跨关和同关重复，无需为了丰富物种制作相同形状的额外美术。UI 风格验证优先复用已批准的真实熊猫与程序占位；若要测试多动物同屏，仅增加少量有确定关卡用途的形状，不能先无限批量生产。
5. **完整玩家流程为发行条件**：首章应包括标题/开始、可理解的首次教学、游戏内拖放与 90°旋转、合法/非法反馈、明确关卡进度、足以从死局恢复的实际操作（重置、撤销或可取回重摆中经体验证明可用的组合）、通关反馈、继续下一关、章节结束及重新游玩。撤销按钮、选关页、复杂教程、特殊动画不是默认独立强制功能；若恢复操作导致明显重复劳动，由 DESIGN 基于实测升级最小方案。
6. **任务与验证边界**：先由 DESIGN 输出 `UI_FLOW_AND_LAYOUT_001` 的尺寸/流程/关卡资源约束，再由 ART 出分层视觉候选，HUMAN 审批精确视觉版本，最后由本地 Codex 接入已批准资产并回归。跨角色工作按单 Owner 分段；前后可在不增加返工风险的情况下并行占位研究。旧三关真实熊猫接入结果保留为局部技术证据，正式 UI 动态布局、完整关卡/教学/章节体验和发行构建在 Codex 实测之前一律 `PENDING/NOT_RUN`。

## 4. 美术风格与拼块造型规范

- **4.1 风格定位**：游戏采用原创、简洁夸张、富有喜剧表现力的二维卡通动物风格。以用户2026-10-21提供的农场动物整体截图及牛头眼神特写作为**审美方向参考**，借鉴粗描边、鲜明色彩、夸张形体、简洁立体表现及幽默表情；**不得描摹或复刻参考角色、具体五官组合、专有图案或素材**。不再将偏写实电影CG、真实毛发纹理或三维渲染作为要求。
- **4.2 形体与姿态**：造型优先服务拼块轮廓及趣味，允许拉伸、压缩、弯曲、卷曲、折叠与头身比例重组，不以真实解剖、脚掌投影或统一视角为限制。物种在实际游戏尺寸必须可辨。**统一视觉语言而非几何模板**：不强制动物共享相同视角、朝向、胖瘦、头身比或姿态。
- **4.3 描边与色彩**：使用清晰流畅、视觉重量协调的**深色粗外描边**，允许因物种配色调整色相、局部粗细；内线可更细或省略。上色以鲜明的大色块为主，可根据视觉需要使用**硬边阴影、局部高光和适量柔和过渡**，但不强制完全平涂，也不以真实毛皮、复杂写实光照或电影级材质作为质量指标。不同动物保留必要固有色和物种斑纹。
- **4.4 面部与角色个性**：眼睛、眉口、耳朵可进行夸张的喜剧化设计，允许大眼白、小瞳孔、发愣、斜视、轻微错位、眯眼、瞪眼或其他非写实表情。面部结构与性格可以因物种及姿态而异，**不强制所有动物复制同一眼型、瞳孔位置或表情模板**。
- **4.5 拼块轮廓**：`occupied_cells`仍是二维逻辑占格真值；绘图轮廓只负责直觉提示。动物不必像俄罗斯方块一样填满每一格，可自然留白、耳角尾局部越界；不得有导致严重误判的大片隐形占格、主体大幅侵入非占格或不合理遮挡。必须在真实目标显示尺寸、邻接及四方向旋转中检验。若无法匹配，ART改姿态或向DESIGN提议形状替代，不能擅自修改逻辑碰撞。
- **4.6 Style Kit与视觉统一**：统一描边语言、色彩组织、简洁卡通形体与整体幽默气质，不按材质细丝密度、阴影数量或同一头身比控制风格。代表性样本验证不同物种特征、不同形态和黑白对比、细长及弯曲轮廓，但**验证样本不自动增加首版正式动物数量**；Style Kit 与每个正式版本仍须 HUMAN 明确G3批准。
- **4.7 独立素材与透明度**：正式角色为无场景、无说明排版的**单体RGBA透明图片**，不烘焙固定世界方向的地面阴影；Alpha边缘需干净且抗锯齿，避免残留底色、白黑边或游离像素。缩放、直通/预乘Alpha与滤镜经实测一致处理，不为新画风默认建设复杂毛发Matting。
- **4.8 验收分工与可访问性**：ART检查物种识别、造型趣味、幽默表情、描边/色块协调、实际棋盘中的占格可读性；HUMAN仅对明示版本执行G3视觉审批。DEV继续负责G1文件/Alpha、G2二维形状/旋转和G4游戏真实运行。文字、关键交互对比度要求和不只依赖颜色的反馈维持V1.0标准：普通文字目标至少4.5:1，大字及关键交互图形至少3:1，G4验证色觉辅助显示；UI功能色、环境色、物种固有识别色分开管理。

## 5. 本地生产路径、资产与额度控制

### 5.1 最短闭环

DESIGN 冻结最小玩法/关卡需求 → ART 提供带版本的单体 RGBA PNG 候选与来源 → HUMAN 审批**确切 G3 候选版本** → 原始 bytes 到达 Codex 本地 `assets/inbox/` → Codex 计算 SHA-256、检查文件/Alpha、G1/G2，按已批准元数据接入并进行 G4 → 完整可玩版通过回归 → Codex `git add/commit/push`，从 GitHub 读取验证 → 发布集合。测试阶段可先用占位数据独立跑逻辑，不依赖美术前置完工；只有正式发布必须满足全部 G1/G2/G3/G4。G3 不以技术 G4 为前置条件。

GitHub **可以存储 PNG 二进制**；历史阻断是不同聊天运行环境不共享原始 bytes 及网络/鉴权限制，并非 GitHub 不支持 PNG。新路线使用 Codex 本地 Git 客户端自动提交资源，而非人工上传或 GPT 连接器传输探针。小规模 PNG 默认普通 Git 管理，不预建 Git LFS/外部网盘平台；仅在真实仓库规模/平台限制出现时评估替代。所有已批准正式素材应按版本保留原始字节，在可运行构建所需目录中提交；开发阶段尚未提交的本地素材只能标 `LOCAL_ONLY_UNVERIFIED`，不能视为可复现仓库版本。避免向 Git 提交访问密钥、私有令牌、任意临时图片。

**字节一致性**：使用原始文件 bytes 直接复制，不再生成或重新导出替代；校验文件 PNG 头、解码、尺寸、RGBA/Alpha、大小和 SHA-256。Git blob SHA ≠ PNG SHA-256。若与经批准版本的哈希不同，停止该文件的正式接入，区分传输重编码、候选版本不一致等；可以保留失败样本作诊断，不得悄悄更换通过值。确实决定采用另一 PNG 须单独升版并由 HUMAN G3 重新确认。历史熊猫 `PANDA_RECT6_CARTOON_candidate_v1` 与 `panda_rect6_v2.png` 是不同版本/哈希，不得合并身份或误称 v2 已提交。原 GPT 容器的 `/mnt/data/` 路径不等于用户电脑上的路径。

### 5.2 额度和人工操作硬性优化规则

1. **减少跨 AI 往返**：DESIGN/ART 一次交付必要的锁定规格、确切版本及失败回执；Codex 自主完成技术迭代，不为每个小修复询问用户或回到旧 GPT 开发页。
2. **批量确定性自动测试**：核心放置/旋转/边界/解空间/关卡数据/Alpha 规则用可重复的脚本批量验证，避免多轮「继续」式运行；截图/浏览器仅用于实际交互、显示与受影响回归。报告区分逻辑 PASS 与 G4。
3. **数据驱动复用**：形状、关卡、物种 PNG 和元数据与公共游戏逻辑分离；增加动物/关卡通常通过数据和资源导入，不复制一套物种专属逻辑。遵守按真实需求最小抽象，禁止为预想功能造重型平台。
4. **失败熔断/根因**：同一原因重复出现先做 Problem Elimination Pass（Delete→Avoid→Absorb→Substitute→Reuse→Optimize）；记录最小复现、失败码、已试方法。一次有针对性的修复后仍无新信息，停止盲目重试，改路径或标 BLOCKED；禁止反复同类 CI 探针和无用轮询。
5. **模型/上下文分级**：清晰、低风险的资源登记、小范围编辑和例行测试优先经济/低推理档；复杂架构、非平凡调试、发布审计再提高推理档，前提是 Codex 当前实际可选且质量达标；**不假设模型/套餐额度固定或必然节省某比例**。优先阅读 README→现行合同→Manifest→State→当前任务/相关文件，不全文反复加载历史聊天、旧提案和全部大文件。
6. **批量交付与最小化用户验收**：每项小任务预设范围/停止条件，一次执行“实现→必要测试→修复→复验→证据→提交”；只向 HUMAN 提供必要视觉确认、重大取舍或确实缺失的本地文件指引。实际性能/额度效果由可核查用量评估，不编造节省值。

### 5.3 不可规避的质量底线

生成器真实能力未知时标 `NOT_RUN`。原生透明失败且确有必要才尝试一条简单通用抠图路线；失败按预算 BLOCKED，不让 Codex擅自重画已获批动物。GitHub 成功提交不等于 G1/G2/G4 PASS；任何自动测试不得替代真人审美 G3 或玩家反馈。七天完整可发布周期要求及变更审批保持 §1 规定。

## 7. 验收门禁与发布判定

| Gate | 验收对象 | 责任 |
|---|---|---|
| G0 | DESIGN 汇总首章内容上限、棋盘/拼块范围、玩家流程、界面状态及资源/返工预算；未冻结数值仍为待定，不据此假报技术 PASS | DESIGN；重大取舍 HUMAN |
| G1 | 实际 PNG/RGBA、Alpha 与边缘污染、元数据、许可、版本/hash、尺寸 | DEV |
| G2 | 四邻接、旋转锚点、图像/格对齐、边界与邻接合成；主观轮廓问题交 ART | DEV 测试 + ART 修视觉 |
| G3 | 物种识别、卡通造型与幽默表情、深色粗描边、色块组织、风格统一及四向旋转的棋盘可读性，批准准确素材版本或批次 | ART 出包、HUMAN 批准 |
| G4 | 真实引擎内的拼块选择/跟随拖拽/旋转/放置、合法/非法反馈、首发最小/最大棋盘与目标缩放下的布局不重叠、恢复操作、教学、关卡完成和章节结束；关卡解与重复性可重放 | DEV 实测、DESIGN 汇总体验 |
| G5 | 后续新增章节或背景时的识别度/逻辑回归；首版无新章节则不适用 | 各专业 Owner |

发布就绪必须有 G1/G2/G3/G4 实际证据、明确使用许可、已提交并读回核实的正式 PNG/源码、可运行的真实构建、完整从开始到章节结束流程与版本一致的清单。合同锁定、合成 CI PASS、生成器探针 PASS、AI 主观体验评语均不能替代真实素材/引擎验收，更不等于真实玩家喜欢。尚未测试一律 NOT_RUN/UNVERIFIED，失败须留复现与所属 Owner。

先用占位棋盘验证一条完整可玩流程，同时用少量真实动物证明生产与画面可行；二者都成功之后才启动正式批量生产，防止长期只优化前置合同和 CI。Steam 商店审核/等待不属于构建运行的技术 PASS。
