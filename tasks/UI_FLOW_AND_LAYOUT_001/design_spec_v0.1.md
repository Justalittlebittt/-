## 1. 产品目标和最小范围

不是做一张精美静态 UI，而是让用户从「开始→理解摆法→拖拽旋转→纠错→通关→下一关→章节结束」完整玩通；同时复用现有真实熊猫与拼图系统。

下列数量仅为 G0 讨论候选，**未经 HUMAN 正式批准不更新 Manifest 的最终内容数字**：

| 条目 | 七天预算下建议基线 | 触发范围削减 |
|---|---|---|
| 首章总关卡 | 8关（教学2＋组合4＋综合2） | 6关（教学2＋组合3＋综合1） |
| 不同逻辑形状/正式动物 | 5种／5张，已批准熊猫算1种 | 4种／4张 |
| 测试棋盘范围 | 3×2 到 6×5，正式关卡可能缩小 | 先缩最高复杂度，而非牺牲基本流程 |
| 每关拼块 | 1–6个，可重复使用同一动物 | 减少同屏拼块数量 |
| 正式环境 | 第一章静态背景1套；可复用主题棋盘和UI样式1套 | 用程序色块/简单背景替代多张图 |
| 发售前必须有的体验 | 开始、教学、游戏、纠错、关卡成功、章节结束、重玩 | 不能删；缩关卡/美术以守住闭环 |

8/5 不等于已经完成几何关卡：须另由 DESIGN 对每关提供原创建模、精确可解证据、近似重复筛查与真人体验修正；不同物种不限制形状，允许同一动物多次出现。扩容至10关／6种只有在7天预算内有可验证余量且经 HUMAN 批准才考虑。正式计时起点仍未设定。

## 2. 关键界面状态及跳转

| 状态 | 进入条件 | 必须呈现 | 离开条件 |
|---|---|---|---|
| START | 启动／重玩返回 | 游戏名、首章主题、开始 | 点击开始 |
| TUTORIAL | 第1–2关首次进入 | 轻量分步说明：拖拽放入→旋转R／屏幕按钮→填满；不需要复杂对话 | 直接在棋盘完成操作，不另建教程小游戏 |
| PLAY | 任意正常关 | 棋盘、待放置动物托盘、当前关卡/总关数、旋转、恢复操作、文字提示 | 拼满棋盘 |
| ERROR_FEEDBACK | 非法放置、越界或输入取消 | 明确失败原因及返回／恢复位置，不只依靠红绿颜色 | 持续游戏 |
| LEVEL_COMPLETE | 每关完成 | 明确成功反馈，下一关按钮不会在提前点击时前进 | 进入下一关 |
| CHAPTER_COMPLETE | 最后一关完成 | 首章完成反馈、重新开始；无需新大幅插画 | 重玩/返回开始 |

- 首版**不强制**独立选关页、暂停菜单、物理折叠托盘动画、音效设置和常驻提示系统。真实玩家测试明确需要时另提变更。
- 死局恢复：保留已放置拼块可拾起、可退回托盘、非法操作恢复、重置本关；DESIGN 在实测中判断是否需「撤销上一步」。只有这些操作实际能有效恢复死局且不制造显著重复劳动才算通过。
- 不强制每关唯一解；一切关卡必须可解，不使用参考游戏原始坐标和布局。

## 3. 动态布局契约

### 3.1 桌面首发目标

- 默认 Windows 桌面／鼠标键盘；R 旋转＋画面内旋转按钮。浏览器窗口验收尺寸：1280×720（主要）、1024×768、800×600（紧凑）。420px 既有测试是技术缩放烟测，**不因此承诺手机版或触屏完整支持**。
- HEADER：标题/章节名、动态关卡进度；MAIN：棋盘主区域＋可滚动待放置区；STATUS/ACTIONS：状态文本、旋转、重置及关卡进退反馈；完成时在相同画布/网页叠加轻量状态层。
- 空间分配建议：宽屏棋盘区域约65%–75%，动物托盘25%–35%，具体由可用尺寸及拼块形状决定；紧凑桌面允许缩放、托盘滚动或调整分区，不能裁掉主要按钮与大拼块。
- **禁止固定托盘Y=405一类的布局假设**：棋盘尺寸、托盘位置、滚动范围、底部操作区域必须从当前可用区域及关卡宽高计算；可复用已有 Canvas/HTML，不强制新 UI 框架或引擎。

### 3.2 约束与交互

1. 计算棋盘像素尺寸使用统一的逻辑 cellScale，取决于棋盘 w/h、预留安全边距和实际棋盘区域；控制格子缩放后，旋转、吸附、命中、预览与图片几何必须共用同一变换。
2. 托盘内容根据真实拼块的**旋转后包围盒**排列，可滚动；托盘缩略图允许与棋盘实尺寸不同，但抓起后的实际拖拽影像和落点映射必须平滑转换，保持抓取点稳定，不突然跳到拼块中心。
3. 棋盘与托盘/标题/操作区不能重叠；大棋盘与6拼块测试下无裁切、不可达拼块、不可见关键按钮或无法投放的情况。缩小窗口时仍能无歧义地区分背景、棋盘、托盘。
4. 任意非法放置须有文字/图形反馈并恢复原始位置或托盘；已放拼块允许拾取、旋转、重新摆放；触控指针 capture/取消已有正确行为不得回退。
5. 需验证最小棋盘3×2／1拼块、中等4×3或5×2／2–3拼块、上限6×5／6拼块的**布局压力样本**；上限样本可以纯占位且不冒充已入库正式关卡。800×600下若形状缩小到无法抓取，应缩范围或调整布局，不能虚报适配成功。
6. 文字与关键按钮符合现行合同可读性/对比度要求；错误提示不只依赖红绿。主棋盘始终是最醒目的视觉信息。

## 4. 视觉与背景资产需求（ART 执行候选）

视觉方向完全继承 V1.4：夸张二维卡通、深色粗描边、鲜明大色块、幽默表情与自由变形；不回退到写实毛发/电影CG。**用户已批准的熊猫PNG保持原字节，不得重画/调色或被背景盖住。**

- 场景关键词：「温暖活泼的动物园入园安置站」。可使用简化木制运输台、运输箱、园区标牌、少量绿植作为**背景装饰候选**，不要将具体道具强绑定玩法/棋盘占格。
- 一张第一章可复用的低干扰背景候选：中心棋盘与托盘所在区域对比低、明暗可读、不会与动物深色轮廓竞争；不在背景上预画格线、按钮、文字或熊猫。
- 棋盘底板、格子边线、托盘、按钮、完成提示优先由程序绘制/统一皮肤参数；ART 可以提出描边粗细、基础配色和装饰参考，但无需每个状态单独导出PNG。
- 先提交**一张完整界面布局概念图**用于 HUMAN 审美判断，再附**分层资源清单与遮挡安全区示意**。概念图不是游戏程序可直接使用的素材；最小实际交付是背景文件＋配色/组件规范（视觉获批后再拆）。
- 为了审美一致性，尽量用当前已批准熊猫原图参与预览；如果当前 ART 无法获取已核验原始 PNG，就在概念图以明确标记的占位替代，不能伪造官方熊猫或宣称它是 G3 通过版。
- 「折叠素材」按用户未具体解释的用语不预先扩展为额外游戏机制或动画；折叠/蜷曲**动物姿态**仍完全允许，托盘折叠动效不列首版必需。
